\subsection{Composition depth is confounded by prevalence}
A raw stratification by the number of latent predicates suggests larger semantic gains for deeper conjunctions. However, deeper conjunctions also have lower teacher prevalence inside the candidate pool, which makes fixed-budget pruning easier. We therefore re-analyzed the per-query 20\% recall deltas with pool prevalence as a covariate. In an exploratory OLS regression of method-minus-dense recall on latent count and teacher prevalence, the latent-count coefficient is $-0.0033$ for Binary1-LS2-int4 ($p=0.58$) and $-0.0026$ for RSA4 ($p=0.67$). We therefore find no evidence in this benchmark that composition depth itself increases the advantage after accounting for prevalence, and we do not use the raw depth trend as a headline result.

\subsection{Live semantic predicates inside HNSW}
The preceding microkernel asks how quickly a fixed candidate array can be scored. We next move the compiled predicate into ANN traversal itself. Dense similarity remains the HNSW navigation score; semantic programs only decide whether a visited node may enter the valid result beam. Semantically invalid nodes remain traversable, so the soft predicate does not disconnect the graph. A dense bound is checked before semantic execution, which avoids touching the predicate program for neighbors that cannot improve the current valid beam.

The reviewer-controlled benchmark uses the strict first held-out split of the 44,072-product source catalog, 1,000 deterministic query items, $K=50$, $ef=128$, and three predetermined sets of three active semantic predicates. For each predicate set, thresholds induce target eligibility fractions of 50\%, 20\%, 10\%, 5\%, and 2\%. Traversal recall is measured against brute-force dense top-$K$ among items passing the \emph{same compiled predicate}; it is therefore a search-execution metric rather than end-to-end semantic relevance. The comparison baseline performs ordinary HNSW search for approximately $mK/s$ candidates and materializes the same semantic predicate only after retrieval, where $s$ is the actual eligible fraction and $m\in\{0.75,1,1.5,2\}$ in the completed run.

The result is more informative than the earlier fixed-postfilter comparison. At 50--10\% selectivity, a $2\times$ over-fetch budget is somewhat faster than live traversal, but it gives up 0.19--0.27 absolute Traversal Recall@50. At 5\% and 2\% selectivity, live traversal is both faster and substantially higher recall than that same budget. Most importantly, \emph{no} tested over-fetch point comes within the predeclared 0.005 recall tolerance of live traversal in any of the 15 conditions. We therefore do not report a matched-recall latency ratio from this run; the correct statement is that the completed over-fetch range failed to reach the live-recall operating point.

The live method reaches between 0.955 and 0.992 Traversal Recall@50 across the individual conditions. Exact result-ID parity with the corresponding custom materialized traversal is 1.0 and is treated only as a correctness check. The incremental live-minus-materialized custom-traversal cost is approximately 96--134\,ns per predicate invocation. On the same Intel Xeon 2.20\,GHz CPU, the scalar 384-D normalized-dot kernel costs 617\,ns, so the incremental predicate cost is about 0.16--0.22 of one dense distance computation. This ratio is stable enough across predicate sets and selectivities to support the narrower claim that predicate execution itself is not the dominant cost of the traversal.

An extended sweep to larger over-fetch budgets is implemented in the public reviewer harness so that a true matched-recall point can be found rather than inferred. Until that sweep is run, the paper makes no claim that live traversal is faster than every possible post-filter over-fetch configuration.
